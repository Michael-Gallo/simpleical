# RFC 5545 1.0.0 Readiness Audit

Audit date: 2026-07-09

## Scope

This audit evaluates the library as a parser against the normative RFC 5545
material in [`docs/specs/rfc5545/`](specs/rfc5545/) and the canonical local copy
at [`docs/specs/rfc5545-icalendar.txt`](specs/rfc5545-icalendar.txt).

The following statuses are used:

- **Compliant**: The normative behavior is implemented and test-backed.
- **Partial**: A useful subset is implemented, but valid forms or required
  semantics are missing.
- **Unsupported**: The capability is outside the current library surface.
- **Non-compliant**: Valid RFC input is rejected, invalid input is accepted, or
  data cannot be represented faithfully.
- **Unverified**: The code may support the behavior, but there is insufficient
  test evidence.

Serialization and recurrence expansion are not required for a parser-only
compliance claim, provided they are documented as explicit non-goals.

## Executive verdict

The current library is **not ready for 1.0.0 as an RFC 5545-compliant parser**.
It both rejects valid RFC input and accepts structurally invalid input.

A 1.0.0 release is feasible as a clearly documented parser for a limited RFC
5545 subset, but several correctness and public-model issues should still be
fixed before freezing the API.

## Compliance summary

| Area | Status | Principal findings |
|---|---|---|
| Calendar stream and envelope | Partial | Multiple calendars and required `VERSION`/`PRODID` work, but an empty calendar is accepted despite the required component rule. |
| Content lines | Non-compliant | Names are case-sensitive, TEXT escaping is not decoded, trailing spaces are discarded, and parameter handling is lossy. |
| Component structure | Non-compliant | Nested top-level components can bypass validation; unknown x/IANA components are rejected instead of ignored. |
| VEVENT | Partial | Ten standard properties are missing; DATE/TZID are unsupported; `DTSTAMP` is not required; the METHOD-dependent `DTSTART` rule is wrong. |
| VTODO | Partial | Broad property coverage, but DATE/TZID are absent, `TRANSP` is incorrectly accepted, and value ranges are not validated. |
| VJOURNAL | Partial | `RRULE` is represented in the model but rejected by the parser; DATE and extensions are unsupported. |
| VFREEBUSY | Non-compliant | Optional `DTSTART` is required, required `DTSTAMP` is not required, and PERIOD lists, duration periods, and `FBTYPE` are unsupported. |
| VTIMEZONE | Non-compliant | Required observances and observance properties are not validated; offsets and TZID references have no semantics. |
| VALARM | Non-compliant | AUDIO wrongly requires `ATTACH`; trigger type/relationship and repeat coupling are not validated. |
| RRULE syntax | Partial | The baseline parser is substantial, but valid DATE `UNTIL`, `BYSECOND=60`, and some BYDAY forms fail while invalid combinations pass. |
| Tests and release process | Partial | Race tests pass and combined coverage is 83.7%, but there is no fuzzing or RFC conformance suite. |

## Confirmed high-impact defects

### Content-line and structural parsing

RFC property names, parameter names, enumerated values, and parameter values are
case-insensitive
([`content-lines.md`](specs/rfc5545/sections/content-lines.md#L110-L113)).
Token dispatch is case-sensitive. A valid lowercase `summary` property is
rejected by [`ical/event.go`](../ical/event.go#L17-L96).

Top-level component starts are not restricted to calendar state in
[`ical/parse.go`](../ical/parse.go#L260-L323). A malformed nested `VTODO` inside
an unterminated `VEVENT` can parse successfully, leaving the parent event
unvalidated.

RFC 5545 requires at least one component and requires unknown x/IANA components
to be ignored
([`calendar-components.md`](specs/rfc5545/sections/calendar-components.md#L40-L64)).
The implementation instead:

- accepts an empty `VCALENDAR` through
  [`ical/calendar.go`](../ical/calendar.go#L23-L30);
- rejects unknown components at
  [`ical/parse.go`](../ical/parse.go#L321-L322);
- rejects extension properties inside components while silently dropping them
  at calendar level.

Trailing spaces are valid value characters, but
[`ical/parse.go`](../ical/parse.go#L194-L229) removes them. This can alter
legitimate TEXT values. The parser also uses `bufio.Scanner` without configuring
its token limit, so any individual physical line longer than the scanner limit
fails.

### Values and parameters

`VALUE=DATE` is unsupported because datetime properties are sent to a parser
that only accepts 15- or 16-character DATE-TIME values
([`ical/property_setters.go`](../ical/property_setters.go#L32-L58),
[`icaldur/time.go`](../icaldur/time.go#L18-L28)). This rejects the RFC's all-day
VEVENT, VTODO, and VJOURNAL examples.

`TZID` and most `VALUE` parameters are discarded. Floating times are returned
as UTC ([`icaldur/time.go`](../icaldur/time.go#L86-L92)), losing the distinction
between floating, UTC, and zoned local times required by RFC 5545
([`date-time.md`](specs/rfc5545/value-types/date-time.md#L37-L105)).

TEXT escapes such as `\n`, `\,`, `\;`, and `\\` are stored literally despite
the TEXT grammar
([`text.md`](specs/rfc5545/value-types/text.md#L17-L49)). Confirmed consequences
include:

- `SUMMARY:Line1\nLine2` remaining escaped;
- `CATEGORIES:A\,B,C` becoming three malformed categories.

Parameter names are case-sensitive, duplicate parameters overwrite one another,
and parameters are retained only for attendees, organizers, and attachments.
`ALTREP`, `TZID`, `RANGE`, `RELATED`, `RELTYPE`, and `FBTYPE` have no semantic
handling. `VALUE` is interpreted only for attachments.

#### Value-type coverage

| RFC value type | Status | Notes |
|---|---|---|
| BINARY | Partial | Base64 attachments are validated and retained as encoded text. |
| BOOLEAN | Partial | Used for RSVP; no general representation exists. |
| CAL-ADDRESS | Partial | Parsed through `url.Parse`; associated parameter validation is limited. |
| DATE | Unsupported | Eight-character calendar dates are rejected. |
| DATE-TIME | Partial | UTC syntax works; floating and TZID semantics are lost; leap second `60` is rejected. |
| DURATION | Partial | Syntax support is substantial, but property-specific positivity and nominal day/week semantics are not preserved. |
| FLOAT | Partial | GEO parses two floats but does not enforce geographic ranges or precision rules. |
| INTEGER | Partial | Values use Go `int`; RFC/property ranges and explicit zero presence are not represented. |
| PERIOD | Partial | Only one explicit start/end FREEBUSY period is supported. |
| RECUR | Partial | Most rule parts parse, but contextual and cross-part rules are incomplete. |
| TEXT | Non-compliant | Escape decoding and escaped list separators are unsupported. |
| TIME | Unsupported | No TIME value representation exists. |
| URI | Partial | Used for calendar addresses and attachments. |
| UTC-OFFSET | Unsupported | Timezone offsets are stored as unvalidated strings. |

### VEVENT

The RFC VEVENT grammar is defined in
[`vevent.md`](specs/rfc5545/components/vevent.md#L19-L61).

The parser omits the following standard properties:

- `CLASS`
- `CREATED`
- `PRIORITY`
- `URL`
- `RECURRENCE-ID`
- `EXDATE`
- `RDATE`
- `RELATED-TO`
- `RESOURCES`
- `REQUEST-STATUS`

Most of these already have fields in
[`model/event.go`](../model/event.go), but they are absent from
[`ical/event.go`](../ical/event.go).

[`validateEvent`](../ical/event.go#L139-L147) always requires `DTSTART`, ignoring
the RFC exception when the containing calendar has a `METHOD`. It intentionally
does not require `DTSTAMP`, although `DTSTAMP` is required by RFC 5545.

DATE-valued all-day events, matching DATE-valued `DTEND`, and the associated
duration constraints are not representable.

### VTODO

VTODO has the broadest standard property coverage, but:

- DATE and TZID semantics are absent;
- `TRANSP` is accepted even though it is not part of the VTODO grammar;
- X/IANA properties are rejected;
- `PERCENT-COMPLETE`, `PRIORITY`, enums, and UTC-only properties lack their
  required range or form validation;
- comma-separated `EXDATE` and `RDATE` values fail because each line is parsed
  as one DATE-TIME.

### VJOURNAL

`Journal.RRule` is public in
[`model/journal.go`](../model/journal.go#L98-L101), but `RRULE` is absent from
[`ical/journal.go`](../ical/journal.go) and is rejected as an invalid property.

DATE-valued `DTSTART`, X/IANA properties, and comma-separated recurrence values
are also unsupported.

### VFREEBUSY

RFC 5545 requires `DTSTAMP` and `UID`, while `DTSTART` is optional
([`vfreebusy.md`](specs/rfc5545/components/vfreebusy.md#L21-L41)).
[`validateFreeBusy`](../ical/freebusy.go#L97-L105) enforces the opposite for
`DTSTAMP` and `DTSTART`: it omits the required `DTSTAMP` check and incorrectly
requires `DTSTART`.

The `FREEBUSY` property permits comma-separated PERIOD values, with either
start/end or start/duration forms, and an `FBTYPE` parameter
([`freebusy.md`](specs/rfc5545/properties/freebusy.md#L20-L55)). The parser
accepts only one start/end pair and implements a non-standard `/status` suffix
instead of `FBTYPE`.

Duplicate `ORGANIZER` values overwrite one another rather than triggering the
single-property check.

### VTIMEZONE

[`validateTimeZone`](../ical/timezone.go#L97-L102) checks only `TZID`. RFC 5545
also requires at least one STANDARD or DAYLIGHT observance and requires every
observance to contain `DTSTART`, `TZOFFSETFROM`, and `TZOFFSETTO`
([`vtimezone.md`](specs/rfc5545/components/vtimezone.md#L138-L148)).

Additional gaps include:

- no UTC-OFFSET format validation;
- no uniqueness check for `TZID` definitions;
- no link between datetime `TZID` parameters and VTIMEZONE definitions;
- no X/IANA property support;
- no validation of VTIMEZONE-specific RRULE restrictions.

### VALARM

[`ical/alarm.go`](../ical/alarm.go#L45-L89) implements ACTION/TRIGGER presence
and most DISPLAY/EMAIL requirements, but:

- AUDIO incorrectly requires an attachment even though it is optional;
- EMAIL attachments are repeatable in the RFC but represented by one pointer;
- DISPLAY can contain properties not allowed by its grammar;
- `DURATION` and `REPEAT` are not required to occur together;
- TRIGGER remains an unparsed string, and `VALUE`/`RELATED` are ignored;
- relative trigger prerequisites are not validated against the parent event or
  to-do;
- unrecognized x/IANA actions cause an error instead of the alarm being ignored.

The relevant requirements are in
[`valarm.md`](specs/rfc5545/components/valarm.md#L96-L151).

### Cardinality representation

[`setOnceProperty`](../ical/property_setters.go#L12-L19) uses a field's zero
value to mean "not present". This cannot enforce cardinality for valid zero or
empty values.

Confirmed examples include:

- duplicate `SEQUENCE:0` being accepted;
- duplicate zero-duration values being accepted.

The model also cannot distinguish an omitted integer property from one
explicitly set to zero.

### RRULE

The RRULE parser has strong baseline coverage: all frequency constants and rule
parts are recognized, most numeric ranges are checked, duplicate parts are
rejected, and `COUNT` plus `UNTIL` is rejected.

However, [`validateRRule`](../rrule/rrule.go#L279-L292) checks only a small
subset of RFC cross-part constraints. Confirmed behavior includes:

- valid `BYSECOND=60` is rejected;
- valid DATE-form `UNTIL=20261231` is rejected;
- invalid `FREQ=WEEKLY;BYMONTHDAY=1` is accepted;
- invalid `BYSETPOS` without another BY-part is accepted.

BYDAY ordinal handling also omits a valid leading `+`, accepts zero and values
outside the 1-53 range, and does not enforce the MONTHLY/YEARLY contextual
restrictions.

Recurrence expansion is absent. This is acceptable for a parse-only library if
it is clearly documented as out of scope.

## Public API risks before 1.0.0

The current public model cannot later gain full RFC fidelity without disruptive
changes:

- `time.Time` cannot distinguish DATE, floating DATE-TIME, UTC DATE-TIME, or a
  TZID-qualified local value.
- `time.Duration` loses nominal day/week semantics across timezone transitions.
- scalar zero values cannot represent property presence.
- extension-property maps cannot preserve repeated values or parameters.
- `Alarm.Attach` cannot represent repeatable EMAIL attachments.
- most property parameters have nowhere to be retained in the model.

These representations should be redesigned before 1.0.0 if full RFC support
remains a goal. Otherwise, the limited representation should become an explicit
and stable part of the subset contract.

Errors are also mostly defined in
[`internal/icalerr`](../internal/icalerr/errors.go), while the README names
`ErrContentAfterEndBlock`. External consumers cannot use that sentinel with
`errors.Is`.

## Test and CI assessment

The following checks passed during the audit:

```text
go test -race ./...
go vet ./...
```

Combined statement coverage, measured with `-coverpkg=./...`, was **83.7%**.
The repository contains 76 `.ical` integration fixtures.

Coverage is strongest for RRULE and DURATION syntax and for the currently
supported happy paths. Important missing coverage includes:

- DATE-valued properties and all-day components;
- TZID-qualified datetimes;
- TEXT escape decoding and escaped list separators;
- lowercase property and parameter names;
- X/IANA properties and components;
- METHOD without VEVENT `DTSTART`;
- comma-separated `EXDATE`, `RDATE`, and `FREEBUSY`;
- nested top-level components;
- VTIMEZONE required-property rules;
- RFC Section 4 complete-object examples.

There are no fuzz tests, property-based tests, serializer round-trip tests, or
RFC conformance corpus. CI runs lint, race tests, and benchmark smoke tests, but
has no coverage threshold, vulnerability scan, or fuzzing gate.

## Documentation and release-contract findings

- [`README.md`](../README.md#L3) still describes the parser as "very much not
  ready".
- The README lists only two deviations, while the implementation has many more.
- The benchmark heading says `v5.1`; the current release lineage is `v0.5.1`.
- There is no changelog or compatibility policy.
- The minimum Go version from [`go.mod`](../go.mod) is not documented.
- [`model/doc.go`](../model/doc.go#L3) refers to a nonexistent `parse` package.
- [`icaldur.ParseIcalLocalTime`](../icaldur/time.go#L95-L101) lacks the godoc
  example required by the repository's contribution rules.
- The scanner and untrusted-input memory limits are undocumented.
- The parser-only scope, lack of recurrence expansion, and lack of a writer are
  not stated clearly.

## Recommended release gates

### Blockers before any 1.0.0

1. Fix component-state validation so malformed nesting cannot bypass component
   validation.
2. Replace zero-value presence detection with explicit property-presence
   tracking.
3. Decide and implement a public datetime/property representation before the
   API is frozen.
4. Implement case-insensitive names, TEXT decoding, DATE, and faithful
   floating/TZID representation.
5. Accept or preserve RFC extension properties and ignore unknown extension
   components as required.
6. Correct VEVENT, VFREEBUSY, VTIMEZONE, VALARM, and RRULE normative rules.
7. Add integration fixtures for every corrected property or invariant.
8. Publish the supported scope, stable error policy, changelog, limitations,
   and minimum Go version.

### Strongly recommended

1. Complete the standard VEVENT and VJOURNAL property sets.
2. Implement PERIOD lists, duration periods, and `FBTYPE`.
3. Validate UTC-only properties, enums, property ranges, UTC offsets, and
   property-specific duration restrictions.
4. Add a local RFC example corpus, malformed-input corpus, and fuzz tests.
5. Add CI coverage and vulnerability checks.
6. Document resource limits for untrusted input.

### Deferrable if explicitly out of scope

- iCalendar serialization and line folding for generated output;
- recurrence occurrence generation;
- global timezone-database integration;
- scheduling or iTIP behavior beyond parsing RFC 5545 fields.

## Release paths

### Full RFC 5545 parser conformance

Complete all normative parsing, validation, and faithful representation gates.
A writer, recurrence expansion, and global timezone database can remain out of
scope as long as the package is explicitly positioned as a parser.

### Stable RFC 5545 subset

Fix the structural, cardinality, and data-corruption defects within the
supported subset; publish an exact support matrix; and describe 1.0.0 as a
stable, parse-only RFC 5545 subset rather than as RFC-compliant.

If future full RFC fidelity is expected, the public datetime and property
models should still be redesigned before this subset API is frozen.
